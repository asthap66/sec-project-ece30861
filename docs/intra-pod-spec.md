# Intra-pod API specification for the endpoint registry

This document gives the pod teams the interface needed to call and test the
Phase 3 incident and evidence API. Both implementations use the common Phase 2
pod specification v1.0, Q5.1-Q5.3, with the Phase 3 scope in Q6.1.

Version: Phase 3 registry handoff, 2026-10-27. This describes the current
repository interface; deployment verification and pod approval of the open
items below remain pending.

## Common request and response rules

- Request and response bodies use JSON with camelCase field names. Send
  `Content-Type: application/json` for JSON request bodies.
- `GET /health` is public. All other business endpoints require `X-API-Key`.
  Missing or incorrect credentials return 401 before routing or validation.
  The current implementation also exposes `/docs`, `/redoc`,
  `/docs/oauth2-redirect`, and `/openapi.json` publicly as documentation paths.
- Request timestamps are RFC 3339 strings with a timezone (`Z` or an offset
  such as `-04:00`). Responses represent the same instant in UTC.
- Required text must be a nonblank string. Submitted text is preserved.
- Resource IDs are generated by the service. Use the returned IDs in later
  calls rather than assuming a particular sequence.
- Incident and evidence records are append-only. Unsupported edit/delete
  methods on registered resource paths return 405 with valid authentication.
- Rejected writes must leave stored records unchanged. Data persists across
  application restarts until reset.

## Phase 3 endpoints

| Method and path | Request body | Success | Expected client errors |
| --- | --- | --- | --- |
| `GET /health` | None | 200 `{"status":"OK"}` | None in normal operation |
| `POST /incidents` | IncidentCreate | 201 `{"incidentId":"INC-001","status":"OPEN"}` | 400 invalid input; 401 unauthorized |
| `GET /incidents/{incidentId}` | None | 200 IncidentDetail | 401 unauthorized; 404 unknown incident |
| `POST /incidents/{incidentId}/evidence` | EvidenceCreate | 201 `{"evidenceId":"EVD-001","recordedAt":"2026-10-27T12:00:00Z"}` | 400 invalid input; 401 unauthorized; 404 unknown incident |
| `POST /reset` | None | 200 `{"status":"RESET_COMPLETE"}` | 401 unauthorized |

IDs and recording times in examples are illustrative. Unexpected server errors
return 500 using the error envelope below.

### IncidentCreate

| Field | Type | Rule |
| --- | --- | --- |
| `title` | string | Required, nonblank; current limit 200 characters, pending pod agreement |
| `description` | string | Required, nonblank; current limit 5000 characters, pending pod agreement |
| `discoveredAt` | timestamp string | Required; timezone required; cannot be in the future |
| `reporterName` | string | Required, nonblank; current limit 500 characters, pending pod agreement |

```json
{
  "title": "Synthetic incident",
  "description": "Synthetic report for cross-team testing.",
  "discoveredAt": "2020-01-01T10:00:00-04:00",
  "reporterName": "Test team"
}
```

Creation returns only `incidentId` and `status`. A newly created incident has
status `OPEN` and no evidence.

### EvidenceCreate

| Field | Type | Rule |
| --- | --- | --- |
| `category` | string enum | Required; `TECHNICAL`, `BUSINESS_IMPACT`, `LEGAL`, or `OTHER` |
| `summary` | string | Required, nonblank; no explicit maximum in current schema |
| `source` | string | Required, nonblank; current limit 500 characters, pending pod agreement |
| `collectedAt` | timestamp string | Required; timezone required |

```json
{
  "category": "BUSINESS_IMPACT",
  "summary": "Synthetic service interruption.",
  "source": "Synthetic operations report",
  "collectedAt": "2020-01-01T11:00:00-04:00"
}
```

Evidence creation returns only `evidenceId` and the server-generated
`recordedAt`. Evidence must belong to an existing incident. No additional
future-date or ordering restriction is imposed on `collectedAt`. Adding
evidence does not change incident status.

### IncidentDetail

Retrieval returns the following structure. Evidence is an empty array before
any evidence is attached. `currentDecision` and `filing` are explicitly null
throughout the Phase 3 increment.

```json
{
  "incidentId": "INC-001",
  "title": "Synthetic incident",
  "description": "Synthetic report for cross-team testing.",
  "discoveredAt": "2020-01-01T14:00:00Z",
  "reporterName": "Test team",
  "status": "OPEN",
  "evidence": [
    {
      "evidenceId": "EVD-001",
      "category": "BUSINESS_IMPACT",
      "summary": "Synthetic service interruption.",
      "source": "Synthetic operations report",
      "collectedAt": "2020-01-01T15:00:00Z",
      "recordedAt": "2026-10-27T12:00:00Z"
    }
  ],
  "currentDecision": null,
  "filing": null
}
```

The response does not include internal `createdAt` or a nested `incidentId`
inside evidence objects.

## Errors and validation order

All errors use this envelope:

```json
{"error":"INVALID_DESCRIPTION","message":"description is required"}
```

| HTTP status | Meaning | Current implementation code |
| --- | --- | --- |
| 400 | Invalid request; field errors name the field in `message` | `INVALID_<FIELD>`, such as `INVALID_DISCOVERED_AT`; `INVALID_BODY` for malformed JSON or invalid body shape |
| 401 | Missing or incorrect API key | `UNAUTHORIZED` |
| 404 | Incident or route not found | `NOT_FOUND` |
| 405 | Method unsupported on a registered path | `METHOD_NOT_ALLOWED` |
| 500 | Unexpected server failure | `INTERNAL_ERROR` |

The pod contract fixes the envelope and status semantics but does not enumerate
all incident/evidence error codes or exact message wording. The codes above
describe this implementation and are not a newly approved shared vocabulary.
Validation uses 400 rather than the framework default 422.

The common validation order is authentication, endpoint/method, incident
existence, body validation, then workflow-state checks where applicable. In
particular, evidence submitted to an unknown incident returns 404 even when its
JSON body is malformed, provided authentication succeeds.

## Reset and cross-team testing

`POST /reset` deletes all stored incidents and evidence in a transaction. The
current implementation also restarts ID counters, so IDs can be reused after a
reset. Do not retain IDs across reset runs or reset while another team is using
the deployment. Only synthetic data belongs in the shared testing service.

For an agreed destructive test window, run the following in PowerShell from
the repository root after privately setting the test key:

```powershell
$env:BASE_URL = 'https://<deployed-host>'
# Set API_KEY privately in this shell; do not commit its value.
$env:ALLOW_DESTRUCTIVE_TESTS = '1'
uv run pytest tests/acceptance
Remove-Item Env:ALLOW_DESTRUCTIVE_TESTS
```

The basic handoff workflow is reset, create an incident, retrieve the returned
ID, attach evidence, and retrieve it again. Also check missing/wrong keys,
invalid required fields, a future discovery time, and an unknown incident ID.
Verify restart persistence without resetting between creation and retrieval.
Record the target URL, deployment commit, run date, results, and reproducible
failures in `docs/test-results/`. No deployed passing result is asserted here.

## Operations outside the Phase 3 increment

These common-contract operations are not implemented in this increment:

| Method | Path |
| --- | --- |
| POST | `/incidents/{incidentId}/decisions` |
| POST | `/incidents/{incidentId}/corrections` |
| GET | `/incidents/{incidentId}/deadline-status` |
| POST | `/incidents/{incidentId}/filing` |
| GET | `/incidents/{incidentId}/timeline` |

They must not be registered as working Phase 3 capabilities. With valid
authentication, these absent paths currently return 404, not a placeholder
success response.
